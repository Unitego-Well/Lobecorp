# 开发规则与工作流程

## 规则来源

仓库根目录的 `AGENTS.md` 是 Lobecorp 项目的直接约束和持久化规范；嵌套的 `run/client/*/AGENTS.md` 只属于对应的嵌套 MCP 仓库。

项目内规则按以下层次读取：

1. 当前用户任务中的项目规则。
2. 通用 `dev-standards` 和 Minecraft `mc-mod-operations`。
3. `intellij-idea-jvm-development` 与 `explore` 等工具/IDE 规则。
4. `.codex/standards/` 和 `.codex/skills/` 的 Lobecorp 专项规则。
5. `.claude/skills/` 的通用 Minecraft、Mixin、IDE 和调试参考。
6. 当前源码、资源、配置和 IDEA 诊断。

文档或 Skill 中的计划不能覆盖当前代码；“计划实施”不等于功能已完成。

## 系统文档维护

- 修改前查看 [系统索引](../systems/README.md) 和相关模块文档，再通过 IDEA 核对当前源码、依赖和引用。文档只作为索引与参考，不完整或过时的文档不能作为重复实现已有能力的依据。
- 修改后更新职责、接口、生命周期、配置、资源、协议和依赖的实际变化；新增、删除或迁移入口时同步索引与链接。
- 在 [修改记录](../systems/changes.md) 留下日期、范围、关键源文件和实际检查结果，区分计划、已实现、历史证据与未验证内容。

## 工具选择顺序

- 优先 IDEA/编辑器的文件、导航、引用、类型、诊断、重构和专用 MCP。
- 其次使用服务 MCP 或官方 API。
- 只有专用工具不能完成任务时，才使用命令行或通用文本工具。
- Java/Minecraft 依赖、原版类或 JAR 内容使用 IDEA/MixinMCP 专用查询，不用 `rg`/`grep` 代替依赖内部查询。
- 不重启 IDEA、不改全局插件、不改变 IDE 配置，除非用户明确授权。

## 修改边界

- 只修改用户明确要求的结果，不顺手重构、清理、重命名、格式化或修复无关问题。
- 修改前读取足够上下文，保留已有暂存和未暂存修改。
- 新文件使用新增补丁，已有文件使用行级补丁；匹配失败时停止，不整文件覆盖。
- 删除前必须确认精确目标并保留备份；本次没有删除操作。
- Java/C# 中可通过 import 使用的类型不写完整限定名调用。
- 业务文本、配置值、规则参数、资源 ID 和可变数值应集中在常量、配置、资源、枚举或注册结构中；语法/API/协议固定值可保留。

## 本地备份与空目录

- 本地备份统一放入根 backups/，按任务名称与日期分目录，保留原项目相对路径和文件内容；目录已由 .gitignore 排除。
- 已有备份目录及归并进度见 [本地备份索引](../../backups/README.md)。迁移不覆盖同名文件，不手动改变已有 Git 暂存内容。
- 包迁移后的空目录只在再次确认没有文件时清理；清单记录原路径，禁止扩展到运行目录、生成输出和嵌套仓库。

## 验证边界

- 小改动（例如只修改数值）只检查相关文件和调用；不主动执行完整编译、数据生成或运行验证。
- 涉及多个系统、多个文件、重构、包迁移、数据结构或网络协议的修改，按大型修改执行完整收尾。
- 大型修改必须通过 IDEA 的运行配置、MCP 和诊断完成项目编译、数据生成、生成资源检查及过时调用检查。
- 不启动 Minecraft、服务器或调试会话，也不通过 MCP 改变世界、玩家或外部服务状态，除非任务明确要求。
- IDEA 的索引状态、文件树、源文件内容和 Git 状态可以作为静态证据，但不能替代构建或游戏验收。

## NeoForge 版本规则

- 当前项目目标为 Minecraft `26.1.2`、NeoForge `26.1.2.100`、Java `25`。
- 不将 1.21.x、Forge 1.20.1、Fabric 或其他版本的注册、事件、数据组件和映射示例直接套入当前项目。
- 当前 Mixin 配置使用 `JAVA_25`；实体、事件、Payload、Attachment 和资源路径以当前 IDEA 映射为准。
- 数据生成输出到 `src/generated/resources`；该目录是只读输出，生成前只修改源，生成后检查是否只产生预期内容。

## 事件订阅规则

来自 `.codex/standards/event-registration.md` 和 `lobecorp-event-architecture`：

- 自动订阅类只能位于 `org.unitego.lobecorp.events` 或子包；客户端入口位于 `events.client` 并保持客户端边界。
- 按功能域拆分订阅类，避免一个总入口承载全部业务。
- 同一事件总线、发行侧和具体事件类型只保留一个入口；不得同时使用注解、`register` 或 `addListener` 重复注册。
- 订阅类负责入口和有序分发，业务处理留在所属域。
- 保留总线、优先级、取消状态、客户端/服务端边界和处理顺序。
- 当前记录特别指出 `LevelTickEvent.Post`、`LivingIncomingDamageEvent` 和客户端渲染修改器的处理顺序，修改这些入口前必须重新检查调用依赖。

## 实体技能、附件和指挥家规则

- `EntitySkillAccess` 是实体技能操作的唯一能力入口；业务调用方不直接操作技能管理器或运行附件集合。
- 技能定义和注册属性由 `IEntitySkill`/`EntitySkill.Properties`/`LcEntitySkills` 负责；运行实例使用非持久化附件，不保存实体、Level、导航或渲染对象。
- `SavedData` 保存世界级队伍目录、远程命令摘要和释放记录，不保存单实体运行实例。
- 指挥家单位字段由附件保存、能力负责操作、世界目录负责持久化队伍和远程摘要；查询不能自动编队。
- 修改附件后必须显式提交/同步并更新目录；修改世界目录后需要 `setDirty`。
- 远程命令由带修订号的待交付记录表达，最后一条意图生效，不建立第二套命令队列。
- 技能结束、取消、卸载、死亡路径应同时清理技能效果和按运行实例绑定的命中框。

## 动画与视觉同步规则

- 持续动作优先使用 `EntityStateHolder`、`LcEntityDataSerializers.ENTITY_STATES` 和状态边沿切换。
- `playAnimation`/`stopAnimation` 表达生命周期边沿，不应每 tick 重发。
- 服务端确认生成的粒子使用 `ServerLevel.sendParticles`；已由技能同步、实体状态或粒子表达的表现不得重复添加 Payload。
- 不使用自定义 `broadcastEntityEvent`/`handleEntityEvent` 编号承载 Lobecorp 自定义视觉事件。
- 动画、粒子、阶段和实体移除路径必须有对应清理逻辑。

## Mixin 规则

- Mixin 只做原版桥接和必要拦截，不复制业务状态机。
- 先确认目标方法的声明类、继承关系、映射签名和当前 Mixin 配置，再选择注入器。
- 参考 `.claude/skills/mixin-master-reference/references/` 中的 Mixin、MixinExtras、MixinSquared 和冲突规避资料。
- Mixin 变更后检查配置、引用、导入、类型、注入点和客户端/服务端边界；不以静态通过代替运行兼容性验证。

## 当前任务确认的通用开发规范

以下规则是当前任务中用户确认的通用开发约束：

1. 对不懂、不理解或可能造成误会的内容及时提问；每次只问一个问题。提问使用“选项 + 推荐意见”的形式，并在用户选择后明确记录选择结果。
2. 优先使用已有 Skill、MCP、工具和 API；项目文件只能通过 IDEA 编辑。IDEA/MCP 不可用或无法完成编辑时，先说明并等待授权，不自动改用 `apply_patch` 或命令行编辑。
3. 文件修改前后都通过 IDEA/MCP 检查相关文件信息。大型修改检查文件内容、错误、警告、语法、引用和 Git 状态；仅修改数值等小改动时只检查相关部分。允许并行处理不同文件，但必须明确文件归属，禁止并行修改同一个文件。
4. 以下任一情况都属于大型修改：涉及多个系统、多个文件、重构、包迁移、数据结构变化或网络协议变化。大型修改收尾必须通过 IDEA 的运行配置、MCP 和 IDEA 诊断完成编译、数据生成及过时调用检查；数据生成输出目录不得手工修改或放入手写内容。
5. 大型修改发现与本次改动无关的既有问题时，只记录并说明需要扩大范围，等待确认；不得将未执行、被中断或环境阻断的操作报告为成功。数据生成完成后通过 IDEA/Git 确认输出只包含预期变更。
6. 优先复用已知 `lib`、API 和接口。新增系统、抽象、接口或依赖前，先通过 IDEA/MCP 检索项目源码、已有依赖和相关 Skill/API 文档；能组合已有能力时不新增。引入新 `lib` 前必须先说明能力缺口、必要性、影响、版本和维护成本，并得到确认。
7. 只有在多处使用、经常变更或属于规则数值时才提取常量；提取出的常量及本次大型修改涉及的既有常量必须添加注释，说明业务含义、单位或取值依据。
8. 可见性只能使用 `public`、`protected` 或 `private`，禁止包私有；规则适用于当前任务涉及的既有成员。默认采用最小必要可见性，必要时通过包装方法提供外部访问，避免直接暴露内部成员。
9. 系统包括功能模块、包、事件、网络、动画、渲染和数据存储等子系统。系统之间必须保持职责隔离和单向依赖；能独立启用、禁用或替换的通常视为弱依赖，否则视为强依赖。强依赖只能通过被依赖系统的公开接口交互，不能直接访问内部实现。发现现有系统违反边界时，仅在当前任务范围内且确有必要时调整，否则记录并等待确认。

### 文件修改与复用补充

- 已有未提交或用户正在修改的文件，先通过 IDEA/Git 对比，再在同一文件中最小范围合并，不覆盖用户修改。
- IDEA 自动格式化、导入优化或文件重排只处理本次修改相关部分，保留无关内容原样。
- 复用 `lib` 或 API 时，以当前项目锁定版本的 IDEA 解析结果和本地文档为准，不直接套用其他版本示例。
- `runData` 生成目录是只读输出目录；生成结果不符合要求时只修改生成源，再通过 IDEA 重新生成。

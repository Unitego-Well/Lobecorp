# 深夜清扫：虚拟浪潮渲染具体实现

核对日期：2026-10-22。本文通过 IDEA 读取当前工作区源码整理，说明已经写入代码的渲染路径，不把最初计划或历史版本当成现状。本轮仅编写文档，没有修改业务代码，也没有重新构建或运行游戏。

## 1. 当前架构与实现边界

当前采用混合渲染：

- 近处：已有清道夫模型的三维几何、共享奔跑姿态和 GPU 实例化。
- 远处：由同一模型与奔跑动画烘焙的顶、前、侧、后四视角动画平面，同样使用 GPU 实例化。
- 过渡带：同一逻辑单位同时提交三维与平面，以互补透明度渐变。
- 所有虚拟单位：不创建 Minecraft Entity，不创建逐个 GeckoLib 控制器，不提交任何虚拟阴影。
- 正常参战实体：独立走原来的实体、AI、命中、死亡和渲染流程，不由这套虚拟渲染器代替。

所以，“保留数量”指保留应当显示的逐个单位与运动，不代表远处仍使用完整三维几何。当前远处已经是用户选择的四视角烘焙方案。

烘焙对象是模型资源和一个循环奔跑动画，不是把测试世界或整条线路拍成背景图。图集由所有同类单位共享，不按每个单位生成。

一帧的逻辑顺序：

```text
提取世界渲染状态
  → 检查资源代际、更新运行时精度
  → 按附近已同步路段解析候选位置
  → 范围／区块／视锥／缓存遮挡检测
  → 按显式上限选取候选
  → 获取显示槽位、光照、LOD、相位、透明度
  → 推进一个图集准备步骤
  → 建立三维和／或烘焙 Draw
  → 保存本帧渲染快照
SubmitCustomGeometryEvent
  → 暂存快照
AfterLevel
  → 跳过 Iris 阴影阶段
  → 准备网格、纹理、实例 UBO 和索引
  → 开始 RenderPass
  → 先不透明，再透明实例绘制
```

SubmitCustomGeometryEvent 暂存步骤有实际必要：当前 LevelRenderer 在 AfterLevel 之前会重置渲染附加数据，不能等到最后再从已清空的状态取快照。

## 3. 不逐个模拟的解析运动

服务器同步种子、线路节点、事件时间、速度、规则和战斗让行区域，客户端不接收每个虚拟单位的位置或骨骼。

客户端用“生成行 row + 横向列 column”构造稳定编号：

```text
number = row × 65536 + column
spacing = 1 / sqrt(density(width, baseDensity))
station = eventTime × speed - row × spacing + 稳定纵向扰动
```

station 是沿线路的弧长坐标。根据当前路段的起止弧长，反算可能出现在该段的 row 区间，只枚举这些行及横向列，不从事件开始累计遍历所有已生成单位。

位置计算包括：

1. 在路段端点之间插值得到线路位置。
2. 对相邻路段的方向做插值并归一化，获得平滑朝向。
3. 根据 column 得到基础横向位置。
4. 加入由种子、编号和连续时间得到的噪声，幅度与间距有关。
5. 加上战斗区域的平滑侧向让行。
6. 用节点横向高度带插值得到地面高度。

每段预先准备五列高度样本、方向和端点；候选计算尽量使用标量，避免每一步创建 Vec3。只有存在让行区域时，该分支仍会创建位置／侧向向量。

让行方向使用出生列的正负侧，避免单位因走到区域中心另一侧而反复翻转方向。区域中心、半径和作用强度随统一时间平滑变化。

同种子、同规则、同线路版本与时间决定基础运动。画质档位只影响表示精度和显式显示选择，不改变服务端战斗。

## 4. 候选选择与数量约束

首先对整条路段做距离与扩大的包围盒视锥检测；整段不可能看到时，不枚举它的行列。

候选进入显示选择前还会检查：

- 到相机的三维距离是否超过有效显示范围。
- 是否仍可能进入显式显示上限。
- 所在区块是否已经加载。
- 模型包围盒与视锥的关系。
- 所属共享空间格上次的地形遮挡结论。

有上限时使用可复用的有界最大堆。评分为距离加少量稳定种子扰动，因此主要保留近处，也避免严格距离截面过分整齐。堆满后，无法超过堆中最差候选的对象尽早跳过。

maximumVisible 默认 5000；-1 使用当前实现可表达的最大整数限制，不额外设隐藏的数千单位上限；0
不选取主体。无限模式仍受范围、区块加载、视锥和遮挡约束，也仍有机器内存及处理时间的实际限制。

rangeChunks 默认 12；-1 跟随客户端有效视野距离。手动范围同样不超过有效视野距离，换算为格数是区块数乘 16。

运行时自动降级不修改 maximumVisible，也不通过随机删掉主体来提高帧率。

## 5. 遮挡剔除的具体做法

### 5.1 空间格共享

HordeVisibility 不对 5000 个单位每帧各发多条射线。它把脚底位置的 XZ 按 4 格分组，Y 按脚底所在整数高度分组。同格单位共享一个
Cell。

格的保守包围范围为：

```text
X: cellX - 1 到 cellX + 5
Y: cellY - 1 到 cellY + 4
Z: cellZ - 1 到 cellZ + 5
```

这比脚底格更大，目的是覆盖模型宽度和高度。格的区块状态及视锥相交结果每帧只算一次；部分相交时，再检查单位自己的包围盒。

缓存使用 Long2ObjectOpenHashMap，避免普通 Map<Long, ...> 的 Long 装箱成本。

### 5.2 射线与复查预算

每帧最多复查 32 个格；每格最多测试九个点：扩展包围盒八角和一个中心点，先测较高的角。

只要有一条射线没有被挡住，就保留整格；九条都被挡住才判为遮挡。相机位于格的扩展包围盒内时直接可见。

射线不检测液体，且只让 isSolidRender 的方块提供碰撞形状；玻璃等不按完整实心遮挡物处理。因此玻璃后面的浪潮仍可显示。

复查间隔至少 5 tick。过期格保留旧结果并排队，不因本帧预算耗尽就突然全部显示。未知格初始可见，按保守方向处理；检测结果在后续选择中使用。相机离缓存锚点超过
2 格时重建缓存。长时间未使用的格会被清理。

### 5.3 准确性和能力边界

这是 CPU 上的预算化粗遮挡，不是 GPU Hi-Z、深度金字塔或硬件遮挡查询。

九点取样不是逐像素可见性的数学证明：细小孔洞、特殊方块形状和快速镜头变化可能产生误判或延迟。单位彼此之间没有单独进行这套射线遮挡剔除。

已经提交的几何仍使用场景深度测试。深度测试会挡住墙后的像素，但不会追回此前已经发生的 CPU 候选计算与顶点处理成本；提前剔除正是为了省下这些工作。

## 6. 显示对象池与光照缓存

ACTIVE 以事件 UUID 和稳定编号索引 Display。离开本帧选集的 Display 放回 POOL；新进入选集的单位优先复用槽位。

Display 保存最近位置、出现时间、最后可见帧、光照采样位置和值等少量信息，没有生命、AI、碰撞箱或实体控制器。

闲置池默认保留 256 个槽位，超额时每帧最多释放 32 个。当前池化范围主要是 Display 和候选堆槽位；每帧仍会产生
Instance、Draw、部分集合和向量，不能称为整条路径零分配。

Key 的 hashCode 对 UUID 和稳定编号做混合，降低规则化行列编号在哈希表中产生集中冲突的风险。

光照使用模型位置上方约一格的原版打包光照。跨采样方块或距离上次采样达到 5 tick 时更新，复用 MutableBlockPos，避免每帧为所有单位重复读光照。

## 7. 近处三维：共享姿态而非逐个骨骼更新

HordeMeshCache 从当前模型、动画资源读取指定奔跑循环，用现有 LcAnimationClip 采样姿态。

烘焙时：

1. 按动画时间得到骨骼平移、旋转、缩放。
2. 按层级递归组合骨骼变换。
3. 调用已有 cube 几何输出，捕获变换后的顶点、UV 和法线。
4. 通过 LcModelLodUtil.shouldRenderCube 应用现有模型细节省略。
5. 保存为共享不可变 Mesh。

不写共享 GeoBone 的 frameSnapshot，不为虚拟单位运行声音、粒子或服务端行为关键帧。

三维分为三个 band：

| band | 动画策略                           |
|------|------------------------------------|
| 0    | 相邻两帧姿态，GPU 做顶点与法线插值 |
| 1    | 直接使用一个采样姿态               |
| 2    | 从少量固定奔跑姿态中按相位选择     |

共享姿态相位默认 8 组，由种子稳定选择；单位不是每帧抽随机动作。

采样率随质量按四分之一档量化，避免缓存键随连续质量值不断变化。近／中／固定姿态的距离也随质量缩放。这个三维 LOD
与独立的“转烘焙距离”是两套判断。

缓存键包含视觉定义、band、帧号与总采样帧数。每帧普通网格构建默认最多 2 个，CPU 网格预算默认 32 MiB。暂时没有目标姿态时尝试使用同定义、同
band 的已有网格；连可回退网格也没有时，该三维 Draw 可能暂时无法生成。

## 8. 四视角动画图集如何生成

### 8.1 触发与准备节奏

当前是首次需要某个视觉定义时懒创建图集任务，不是在游戏启动屏幕一次性预烘焙全部资源，也不写入持久化磁盘缓存。

默认一个奔跑周期采样 12 帧，每个视角单元 96×96 像素。准备分两阶段：

- 每个推进步骤先采样一个完整三维姿态，共 12 个。
- 姿态齐备后，每个推进步骤把一个姿态光栅化为四个视角，共 12 个步骤。

所有定义每帧合计只推进一个待处理任务。因此单个默认图集通常需要约 24 次推进，另有创建时序与最后纹理上传成本；不是严格保证固定毫秒预算，也不是后台线程异步任务。

图集准备完成前 atlas 为 null，继续选择三维路径。资源加载或光栅化失败会记录警告，保留三维路径。

### 8.2 四视角与统一边界

先遍历整个周期所有姿态顶点，求共同的水平半径、最低 Y 和最高 Y，并留少量边界。所有帧使用共同范围，避免奔跑时平面尺寸不断伸缩。

四列分别为：

| 列 | 视角 | 投影平面 | 深度 |
|----|------|----------|------|
| 0  | 顶   | X、Z     | Y    |
| 1  | 前   | X、Y     | Z    |
| 2  | 侧   | -Z、Y    | X    |
| 3  | 后   | -X、Y    | -Z   |

每一行对应一个奔跑帧。左右侧共用侧面图，通过 GPU 镜像 UV 区分，并没有另烘焙第五个视角。

默认图集尺寸为 384×1152：四列乘 96，十二行乘 96。每个单元保留 2 像素透明边缘，UV 映射到内部，降低相邻单元串色。

### 8.3 CPU 光栅化

当前不调用实体渲染器拍截图，也不使用 GPU 离屏场景渲染。HordeImpostorRasterizerUtil 直接处理共享姿态网格：

1. 每个四边形拆成两个三角形。
2. 按对应正交视角投影到图集单元。
3. 扫描三角形像素包围范围。
4. 用重心坐标判断像素是否位于三角形内。
5. 插值深度、UV 和基础明暗。
6. 通过深度数组保留该像素最前面的表面。
7. 从原清道夫纹理取色；透明度小于约 0.1 的像素跳过。
8. 同时采样原 _glowmask，写入独立发光图集。

基础明暗为 0.6 + 0.4 × max (normalY, 0)，不是烘焙测试世界的夜间光照。世界亮度在绘制时仍由原版光照图提供。

颜色和发光各一张 RGBA 图。按每像素四字节计算，默认两张基础图像约 3.375 MiB，不包含对象、GPU 管理开销或任何额外副本；不是每个单位占这么多。

图集完成后注册为共享 DynamicTexture，并上传 32 字节边界 UBO，包含尺寸、高度、帧数和图集布局。临时姿态与源图像随后释放。

## 9. 远处平面如何随视角和时间变化

远处每个单位只使用一个共享四边形，四顶点、两三角形。

顶点程序根据“相机相对于单位的位置”和单位朝向，得到模型局部视角：

- 相机高度差大于水平距离时选择顶视图。
- 否则比较局部横向和纵向分量，选择前、侧或后。
- 左侧方向使用侧视图并镜像 UV。
- 顶视图构造水平平面，随单位朝向旋转。
- 其他视角构造朝向相机水平位置的直立平面。

动画相位为：

```text
phase = fract(eventTime / 20 / runCycleSeconds + phaseGroup / groupCount)
frame = floor(phase × bakedFrameCount)
```

远处当前是离散取一张烘焙帧，没有相邻图片帧混合。四个视角之间也没有连续角度混合，因此绕单位观察时可能存在视图切换，不能等同于完整三维模型的连续轮廓和视差。

烘焙图集只保存颜色与发光，没有逐像素深度图或法线图；参与场景深度的是平面本身，近距离穿插与倾斜观察的深度准确性有限。这也是近处保留三维的重要原因。

## 10. 三维与平面的透明度切换

默认 distance=32，过渡宽度固定为 4 格：

```text
blend = smooth((cameraDistance - 32) / 4)
三维透明度权重 = 1 - blend
平面透明度权重 = blend
```

- 32 格及以内：三维。
- 32～36 格：两种表示同时提交。
- 36 格及以外：图集准备好时只提交平面。

单位最终 alpha 是显示加入淡入、路线起终点淡入淡出、以及当前表示权重的乘积。事件 fadeTicks 默认 5 tick。

过渡带一名单位会产生两个 GPU 实例提交，所以 5000 visible 时 submissions 大于 5000 是合理现象，并不表示逻辑单位增加。

互补透明度只是权重互补；普通 alpha 混合叠加并不保证总遮盖率严格恒定。当前不是抖动透明、逐像素互斥过渡或顺序无关透明，密集交叠仍可能出现亮度及排序瑕疵。

## 11. GPU 实例数据与几何驻留

### 11.1 三维网格

每个 GPU 顶点为 40 字节，包括：

- 第一姿态位置。
- 纹理 UV。
- 打包在 Color 中的第一姿态法线。
- 第二姿态位置。
- 第二姿态法线及对齐字节。

第一次使用某一对共享 Mesh 时上传一次 GPU 顶点缓冲，后续直接复用。每帧不再为每个清道夫逐顶点变换并写入 BufferBuilder。

三维顶点程序执行：

```text
localPosition = mix(firstPosition, nextPosition, interpolation)
localNormal = normalize(mix(firstNormal, nextNormal, interpolation))
worldRelativePosition = yawRotate(localPosition) + cameraRelativeInstancePosition
clipPosition = projection × modelView × worldRelativePosition
```

### 11.2 每单位 32 字节

每个实例只上传两个 vec4：

| 数据   | 内容                                                       |
|--------|------------------------------------------------------------|
| vec4 A | 相机相对位置 X/Y/Z、最终 alpha                             |
| vec4 B | cos(yaw)、sin(yaw)、插值系数或图集相位、打包光照及发光标记 |

没有发光贴图时通过光照值的负数编码表示，着色器再还原原始光照值。

5000 次单表示提交的有效实例参数约 160000 字节／帧。实际上传还包含 UBO 分块对齐及尾部空位，过渡带重复提交也会增加上传量。

### 11.3 分组与绘制

按网格对、纹理、透明／不透明状态、图集分组。每组再分成最多 256 个实例的块；一个块的 UBO 数据为 8192 字节，并按 GPU uniform
offset alignment 对齐。

256 是单次绘制容量，不是浪潮总上限。若全部 5000 个单位恰好同组且没有过渡重复，需要至少 20 个 draw；实际还受姿态、材质和透明状态分组影响。

所有实例缓冲扩容、网格上传、索引准备和纹理取得都在开启 RenderPass 前完成，避免在 pass 中执行资源上传。实例缓冲按容量增长复用。

CPU 和 GPU 网格分别有自己的缓存管理。GPU 网格使用访问顺序，当前帧未使用且超过缓存预算或闲置超过 1200 帧时释放；不能把
meshCacheMiB 当成整个系统总显存上限。

## 12. 深度、透明、光照、发光与雾

### 12.1 深度与透明

创建八种管线组合：三维／烘焙 × 不透明／透明 × 正向／反向深度。

不透明使用默认颜色输出并写深度。透明使用 TRANSLUCENT 混合，保留深度测试但不写深度。双面绘制，不开启背面剔除。

Draw 先按单位距离由远到近排列，GPU 阶段先画不透明再画透明。随后仍会按材质和网格分组，因此不保证所有透明单位跨组保持严格全局排序，也不做逐三角形排序。

### 12.2 发光

顶点程序解包原版天空／方块光照，从 16×16 光照图采样，并乘基础法线明暗。烘焙平面使用向上法线，图集本身已包含模型基础明暗。

片元阶段大致为：

```text
color = max(albedo.rgb * lighting.rgb,
            glow.rgb * glow.a * hasGlow * 0.5);
alpha = albedo.a * instanceAlpha;
```

发光是不随环境光完全变暗的自发光外观。主体与 glowmask 在同一次几何提交完成，不为发光重复整模绘制，不生成动态照明，不照亮地面或邻近单位。

透明贴图像素低于 0.1、实例 alpha 几乎为零时 discard，避免图集透明背景写深度。最终继续应用原版环境雾和渲染距离雾，发光部分同样受雾影响。

这不是光影包专用发光材质协议，也不保证任意包的 bloom 会按其自身实体材质规则识别。

## 13. Iris 兼容和虚拟阴影

HordeIrisShadows 只在 Iris 存在时查询：

- 当前是否为阴影 pass。
- 当前启用光影时是否使用 Reverse-Z。

阴影 pass 直接跳过虚拟绘制。虚拟主体在世界颜色阶段完成后、手部绘制前，通过独立 RenderPipeline 写入主颜色目标，并使用主深度目标。

普通深度使用 LESS_THAN_OR_EQUAL；反向深度使用 GREATER_THAN_OR_EQUAL。这样能继续利用场景深度遮挡，并避免让光影包替换自定义顶点实例变换。

本系统不提交虚拟地面影子，也不提交 Iris 阴影几何，不实现天空遮罩或全局 main wrapper 挖洞。

兼容范围有明确限制：不接入包专用 GBuffer、材质分类、动态阴影或延迟光照；绘制位置也意味着它与包自身后处理的组合需要实际测试。此前本地最小测试包的通过不能推广为所有完整光影包都已兼容。

## 14. 自动降级、资源重载与释放

自动精度基于帧间隔的指数平滑值，目标默认 60 FPS。超过目标帧时间的 1.15 倍时快速降低质量；至少延迟约 2 秒后才慢速恢复。最低质量默认
0.25。

它目前主要调整三维模型分档距离、共享姿态采样率及附属表现精度，不修改显式数量上限。帧间隔不等于本系统单独 CPU/GPU
耗时，垂直同步、窗口状态、其他 Mod 和整个世界负载都可能影响该判断。

检测到 GeckoLib 已烘焙模型代际变化时，释放三维网格、GPU 几何和图集。图集帧数或分辨率改变时重建图集。退出世界清理事件镜像、对象池、候选缓存、声音、可见性缓存和
GPU 资源。

TextureManager 拥有的原始模型纹理只借用；系统自己登记的动态图集通过 manager.release 释放；自己创建的 UBO、GPU 顶点缓冲及
native 上传内存明确关闭。

## 15. 为什么这些优化能保留数量

| 原有成本                 | 当前处理                                 |
|--------------------------|------------------------------------------|
| 每个单位创建和维护实体   | 客户端解析显示，虚拟单位不创建 Entity    |
| 每个单位计算骨骼和控制器 | 共享少量姿态／共享动画图集               |
| 每个单位逐顶点变换并上传 | 网格驻留 GPU，每单位只上传 32 字节       |
| 远处仍处理完整模型顶点   | 远处每单位一个四边形                     |
| 发光重复提交整模         | 同片元程序合成颜色与 glowmask            |
| 大量虚拟单位投影         | 完全去掉虚拟阴影                         |
| 每单位每帧多次射线       | 空间格共享、缓存、每帧复查预算           |
| 遍历事件历史累计个体     | 根据当前路段和时间反算相关行             |
| 大量临时候选和装箱键     | 复用候选堆槽位、标量计算和 primitive map |

保留数量仍有成本：可见单位的位置推算、排序、分组、实例上传及像素覆盖不会消失。尤其密集平面可能反复覆盖同一屏幕像素，透明过渡还会加重
overdraw。远处减顶点后，瓶颈可能转到 CPU 候选处理或 GPU 像素填充，必须重新测量，不能仅凭实例化就保证 60 FPS。

## 16. 当前验证与未完成项

历史夜间 5000 单位运行复验确认：普通 Run 可从纯三维切到四视角烘焙，切换后持续运行，没有再出现本次目标着色器编译崩溃。该修复是将顶点程序共同阶段的
vec4 view 改为 viewPosition，避免与烘焙分支 int view 重名。

完整证据见 [2026-10-22 运行复验](horde-shader-retest-20261022.md)。本文不是新一轮性能报告，未新增 FPS、JFR、GPU 时间或光影包验收。

仍需明确保留的限制：

- 5000 单位稳定 60 FPS 尚未完成正式验收。
- 四视角切换、透明交叠、平面深度及模型不对称镜像需要专项视觉检查。
- 遮挡为有限采样与缓存，存在误差和延迟。
- CPU 仍有每帧分配、候选枚举、排序和分组成本。
- 图集准备是每帧一个步骤，不是按毫秒预算，也没有启动预加载或磁盘缓存。
- 网格、图集和整个客户端总内存不是同一个预算。
- 常用完整 Iris 光影包仍需分别测试。
- 真实参战实体的正常渲染和战斗性能不由虚拟图集优化直接解决。

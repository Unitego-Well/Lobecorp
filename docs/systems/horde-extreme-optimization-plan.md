## 0. 最极端情况定义

“极端”按负载、环境、判定三层定义。只有 E1/E2 属于本方案的承诺范围，E3 是环境上界，E4 是可用性兜底。

| 级别 | 负载 | 环境 | 判定（必须达到） |
| --- | --- | --- | --- |
| **E1 极端基线** | 单事件 **10,000** 虚拟实例；1 个事件；真实区域 13 个、光照区段 584 | Iris 1.11.4 + ComplementaryReimagined r5.9.3；2560×1494 最大化聚焦；VSync 关；不限帧；20 TPS 集成服务器；**热机**（GPU ≥80 °C、≈127 W、≈1.90 GHz） | 稳态 **≥60 FPS**（帧间隔 P99 ≤20 ms）；稳态无 >80 ms 帧；GameRenderer GPU ≤15 ms；**绘制数量 == 配置值（默认 10,000）**；允许 LOD/降精度但近景全精度 |
| **E1-拉伸** | 同上 | 同上 | ≥50 FPS（P99 ≤22 ms）。达标后才考虑 60 |
| **E2 极端叠加** | 2 事件 × 5,000 = 10,000；另加 64 真实清道夫 + 粒子开启；区域 ≥20 | 同上 | ≥40 FPS，P99 ≤35 ms；真实实体路径不退化（对照单跑 64 实体） |
| **E3 环境上界** | 同上 | 阴影距离 32、夜间、透明排序、远程多玩家（非集成服） | 不崩、不永久停显；P95 ≤50 ms 且记录可见性；不承诺帧率 |
| **E4 降级可用** | 任意 | Iris 布局不支持/显存不足/资源重载中/窗口尺寸变化 | 不崩、不永久 `failed`、可自动恢复；截图可证明未错位 |

**不列入目标：10,000 实例 + 光影 + 60 FPS。** 原因见 §2 的物理下限：每帧要产出 5.2 M 顶点 / 291 MB 并交给 Iris，60 FPS 意味着单向 17.5 GB/s、若走主机往返则 35 GB/s，超过本机 PCIe 实测能力。要 60 FPS 必须做**减少顶点/可见数量或改渲染架构**，属产品决策，见 §8。

## 2. 预算与物理下限

| 量 | 数值 | 推导 |
| --- | --- | --- |
| 每实例顶点 | 520（130 quad × 4） | `sweeper_a` 烘焙 |
| 每帧顶点 | 5,200,000 | 10,000 × 520 |
| 每顶点字节（Iris 56 B） | 56 | `horde_iris_vertices.fsh` 14 字 |
| 每帧展开字节 | **291,200,000** | 5.2M × 56 |
| 每帧展开片元 | **73,048,064** | 291.2 MB / 4 B |
| 每帧 copy 字节 | ≈291.3 MB（实测） | 每块行对齐 |
| 若 copy 为主机往返 | ≈582 MB/帧 | 回读 + 再上传 |
| 30 / 40 / 50 / 60 FPS 所需单向带宽 | 8.7 / 11.6 / 14.6 / 17.5 GB/s | 291.2 MB × FPS |
| 双向往返所需带宽 | ×2（17.5 → 35 GB/s） | 与 PCIe 4.0 x16 实测约 22–25 GB/s 对比 |

结论：

1. **E1（40 FPS）必须把 expand 从 21.6 ms 压到 ≈13 ms 以下，同时让 copy 与材质重叠**；仅靠 copy 优化不够。
2. **E1-拉伸（50 FPS，20 ms）需要 expand ≤10 ms 且 copy 基本被隐藏**，是本方案的性能极限。
3. **60 FPS 不成立**，除非减少顶点数/可见数量或不再走"真实 Iris 顶点"路径。这一点必须由用户决策，不能在实现里静默减量。
4. 每块 3.88 M 片元用 1.15 ms ≈ **3.4 Gfrag/s**，远低于该 GPU 的片元吞吐能力 ⇒ 当前每块耗时主要是 **pass/fence 同步与依赖取数**，不是纯 fragment 算力。这是 W1 先行的依据。

## 3. 优化工作流

每项包含：依据 → 假设 → 改动 → 预期 → 风险 → 验收 → 回滚。全部改动默认不改变可见数量、LOD、发光、20 FPS 动画，除非 §8 的产品决策明确允许。

### W1（P0）拆掉"每块串行链"

- **依据**：`MAX_WORDS = 4 Mi words`（16 MiB 纹理 + 16 MiB 顶点缓冲）⇒ 576 实例/块 ⇒ **18.7 块/帧**；每块固定 1 个 expand pass + 1 次 `copyTextureToBuffer`（`RenderSystem.queueFencedTask` 建 fence，`executePendingTasks` 帧首 `glClientWaitSync`）+ base pass + glow pass ⇒ 62.2 passes、18.7 次 fence。JFR 已记录 `IrisVertices.draw:620 createRenderPass → glBindFramebuffer`、`:646 → createFence/glFenceSync`、`:639 finishRenderPass`、`:700 glUseProgram` 每块各一次。
- **假设**：expand 单块 1.15 ms 中相当一部分是等待上一块的 copy/材质完成；减少块数或允许重叠可显著下降总时长。
- **改动**：
  1. **单常量实验**：`MAX_WORDS 4M → 16M`（块数 18.7→4.7；纹理+缓冲 64+64 MiB）。
  2. **双缓冲**：2 套（纹理+缓冲）轮换，让第 N+1 块 expand 与第 N 块 copy/材质重叠；块数保持 4.7 时显存约 256 MiB。
- **预期**：passes 62→≤20、copies 18.7→4.7；expand 总时长 −15~30%；整帧 GPU −10~25%。
- **风险**：显存上升（6 GB 卡可接受但需记录峰值）；块变大后单块 stall 变长；多事件时块数翻倍。**不做自适应缩小前不得上线。**
- **验收**：同轮 A/B（4M vs 16M vs 双缓冲），记录 `passes/copies/expand 单次与总时长/整帧 GPU/显存峰值`；E1 ≥35 FPS 或 expand 总时长 −15%。
- **回滚**：单常量回退；双缓冲通过开关关闭。

### W2（P0）expand shader 去重复求值

- **依据**：当前 `horde_iris_vertices.fsh` 每片元重算 `pixel/words`、`ordinalVertex`、`row/column`、`phase/frame/frameStart`、`sin/cos(angle)`、`mat2 yaw`；这些量在同一实例的所有顶点/字上相同，14 个字里 5 个（位置 3 + 法线 + 切线）都要用 yaw 与 frameStart。
- **假设**：把这 5 类量在 motion pass（或一次 per-instance prepass）里算好，expand 改为 1–2 次 fetch，可降 10–20% expand。
- **改动**：`MOTION_VALUES` 5 → 8（位置 xyz、light、sin、cos、frameStart、visible），或新增一张 per-instance 小纹理；expand 直接读。必须保留 float32 位置与 20 FPS 帧语义。
- **预期**：expand GPU −10~20%；E1 拉伸档的关键增量。
- **风险**：运动缓存布局变更影响 motion/shaders/参数；需逐字节/像素回归。
- **验收**：展开纹理 readback 哈希（改造前后同帧一致）；截图 diff 0；三轮同轮 A/B。
- **回滚**：保留旧字段布局，按开关切换。

### W3（P0）copy 与材质重叠

- **依据**：copy 占 8–15%，且当前每块 copy 后立刻材质绘制，下一块 expand 又要等同一纹理/缓冲；fence 在帧首统一等待。
- **改动**：W1 双缓冲落地后，将块 N 的 base/glow 与块 N+1 的 expand/copy 交错提交；`queueFencedTask` 回调改为空（现状已经是空），但要把等待点从"帧首全部 fence"改为"每块自己的 fence"，避免帧级同步。
- **预期**：copy 占比 <3%；整帧 −2~5 ms。
- **风险**：GL 即时流下"先提交后等待"的时序必须实测；Iris 管线切换可能强制同步。
- **验收**：GPU 时间线与整帧 GPU 下降；无错位/幽灵顶点。

### W4（P1）材质 pass 跨块合并

- **依据**：62.2 passes 中约 37.5 来自每块的 base+glow。W1 双缓冲后块间不再共用同一缓冲，可在同一 pass 内循环 `drawIndexed(baseVertex,…)`。
- **改动**：每层 1 个 pass，块内按材质分组；`DynamicTransforms`/lightmap/overlay 提到循环外。
- **预期**：pass 数 −30；base+glow −20~30%（约 0.6–1 ms）。
- **风险**：多材质/多纹理切换顺序；跨事件资源代际。
- **验收**：draws 不变、passes 下降、截图一致。

### W5（P2）motion pass 精简

- **依据**：motion 0.77 ms/帧；`horde_motion.fsh` 每实例 6 次 `movingLocation`（3 分量各 1、朝向 2、光照 1）。
- **改动**：先做 CPU 预混合区域（12 fetch→6）与区域早退；或新增"位移缓存 pass"把昂贵求值 6→3。
- **预期**：−0.3~0.5 ms；优先级低于 W1–W4。
- **边界**：不能用 MRT/浮点附件（26.1.2 不支持）；不能转 CPU 逐单位变换。

### W6（P2）光照与 CPU 集合

- **依据**：光影轮 light CPU 0.49–0.56 ms/帧；`HordeLightField.requiredSections` 每逻辑刻新建 `Section` 并插入 HashSet（L137），JFR 分配权重显著。
- **改动**：`Section` 用 long 打包（x/y/z 位域）；按 Block 缓存候选集合；`batches.distinct()`/槽位遍历只在集合变化时执行。
- **预期**：light CPU P95 ≤0.5 ms、每帧分配下降；同时对无光影路径有益。
- **验收**：同场景每帧分配、light 阶段 CPU、帧间隔。

### W7（P2）首帧与预编译

- **依据**：普通轮 STABILIZE 最大帧 280 ms、sweeper 场景 1307 ms；光影轮 STABILIZE 最大 366–536 ms；`HordeRenderMetrics` 显示首周期 prepare/motion 尖峰。
- **改动**：在正确 GPU 上下文用 `GpuDevice.precompilePipeline` 预热已知管线；模型烘焙按"解析/骨骼/帧/上传"分阶段并给预算；header 到达即预热（线路分页通常有数十 tick 提前量）。
- **验收**：首个事件可见帧 ≤100 ms；无半成品；重载后不重复全额阻塞。

### W8（P1）极端鲁棒性

- **依据**：布局不支持时 `entityVertexWords()` 抛异常 → 事件永久 `failed`；显存/容量不足会抛 IllegalArgumentException；Iris 重载会换布局。
- **改动**：不支持布局 → 回退实例化快路径并退避重试；块大小按可用显存自适应（4M↔16M），并记录降级原因；资源重载后自动恢复；多事件共享块预算。
- **验收**：E4 全矩阵通过（切包/重载/关光影/改窗口/多事件）。

## 5. 实验方法（对抗环境噪声）

1. **同轮交错 A/B**：同一会话内切换开关/常量，至少 3 轮交替（A/B/A、B/A/B），用同轮差值判定。
2. **环境固化**：窗口 2560×1494 最大化聚焦、VSync 关、不限帧、视距/模拟 12；每轮记录 GPU 时钟/功率/温度（5 s 采样）、`throttle_reason`、`gpu_started/completed/skipped`、HEAD+dirty。
3. **指标口径**：同时保留 BenchMod 帧间隔（MEASURE 全窗口）与 GameRenderer GPU/CPU（30 s 子窗口）；阶段用"整帧求和 + 轮换单次"两套；不互相换算 FPS。
4. **正确性闸门**：展开纹理 readback 哈希（同帧逐字节）、截图 diff、夜间发光、动画帧、资源重载。
5. **判定**：P50/P95/P99/最大 + 分布形态；环境差异 >5% 作废重跑；单轮不得下因果结论。

### 8.1 60 FPS 的可行性重算（必须新增减面）

60 FPS 预算：帧 ≤16.7 ms、GPU ≤15 ms、CPU ≤8 ms。当前 GPU 32.5 ms，需 **−54%**。

| 手段 | 预计 GPU 收益 | 说明 |
| --- | --- | --- |
| W1 去串行 | −10~25% | passes 62→≤20、copies 18.7→4.7 |
| W2 expand 预计算 | −2~4 ms | 展开 shader 去重复求值 |
| W3+W4 重叠与合并 | −2~4 ms | copy 隐藏、材质 pass 合并 |
| **W0 静态减面** | **−15~35% 顶点** | 剔除模型内部/不可见面；外观需 A/B 验证 |
| **W9 距离质量档** | **−30~50% 顶点**（按档位） | 远处单位降低顶点数；**可见数量不变**，需配置与质量说明 |

结论：**W1–W4 全落地后约 18–24 ms，仍到不了 60 FPS；必须叠加 W0，并实施 W9 质量档**。W9 是产品级取舍，用户已选择 60 FPS 目标即视为授权，但必须满足：
1. 质量档是**显式配置 + 文档说明**，不是静默减量；
2. 可见实例数量仍为 10,000（不减少数量，只降远处细节）；
3. 屏幕近景（默认 ≤48 格）保持全精度，远景档位切换需无跳变（按块距离，不按相机距离逐帧抖动）；
4. 截图 A/B、夜间发光、动画帧与资源重载全部通过；
5. 若在“可接受外观”下 60 FPS 仍不可达，**停止并上报**，不得继续降低画质强行达标。

### 8.2 新增工作流

#### W0（P0）静态减面（质量中性优先）

- **依据**：`sweeper_a` 130 个非零 quad（23 cube），大量面位于模型内部或相邻 cube 交界，永远不会被看到；它们贡献了 291 MB 中的固定比例。
- **改动**：离线对每个 GeckoLib 模型求“可见 quad 集合”（相邻 cube 共享面上的面剔除；动画摆动幅度内仍可能露出的面必须保留），生成减面后的静态几何与逐帧顶点缓存。**不改变顶点语义**（仍 56 B Iris 格式），只减少数量。
- **预期**：顶点数 −15~35%（取决于内部面比例）；若与 W9 叠加，可支撑 60 FPS。
- **风险**：动画过程中露出被剔除的面（需按骨骼摆动范围留安全边距）；多模型共用 GEOMETRY 缓存需按 visual 分别生成。
- **验收**：逐帧截图 A/B（含极限摆臂/转身）、夜间发光、模型边缘无破洞；顶点数下降记录。
- **回滚**：按模型开关；保留旧几何生成路径。

#### W9（P0，产品级）距离质量档

- **依据**：E1 需要 −30~50% 顶点；只靠 W0 不够。
- **改动**：每个模型生成 2–3 个档位（全精度 / 中 / 低）；按**绘制块到相机距离**选择档位（块级，避免逐单位抖动）；帧缓存与 workspace 按档位共享；`MAX_WORDS` 与双缓冲按档位重算块边界。
- **预期**：远景顶点数降至 40–60%；配合 W0/W1 达到 E1 60 FPS。
- **风险**：档位切换可见（需淡出/块级切换）、远景发光/切线需保持、Iris 布局不变。
- **验收**：E1 60 FPS；切换处无跳变截图；夜间发光；数量仍 10,000。
- **回滚**：质量档可配置为“全精度”，此时退回 40 FPS 档。

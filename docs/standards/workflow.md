# Lobecorp 工作流程与收尾规则

本文件从项目根 AGENTS.md 按职责拆出，与根文件具有相同约束效力；仅在文件修改、工具操作、接口复用或收尾涉及对应规则时读取适用章节。用户当前明确指令仍优先。拆分不改变原规则，不授权顺带修改或主动运行。

## 开始任务前

- 处理开发任务前，先读取相关 Skill、项目规范和专项规范，并制定简要计划。
- 优先通过 IDEA/MCP 做只读检索来确认术语、类型、引用和现有实现；仍无法确定时再向用户提问。
- 不能理解、存在歧义或可能造成误会的内容，必须及时提问，不得自行猜测。
- 每次只问一个问题；提问使用“选项 + 推荐意见”的形式，并把推荐选项放在第一项。用户选择后，明确记录选择结果。
- 澄清与选择问题默认直接使用文本提问，不调用 `request_user_input`、`request_user_input_async` 等提问 API；计划模式允许使用选项 API，一次仍只询问一个实质问题。用户尚未回答时，不视为已选择或确认。
- 涉及向后兼容、旧格式读取、迁移或兼容分支时，默认先询问用户是否需要兼容，不自行保留或新增兼容逻辑；用户已明确选择时按该选择执行，不重复询问。本次模型特效文件采用 `.mfxproj`、`.mfx`、`.mfxpack`，不兼容此前模型工程与定义格式。

## 系统文档与修改记录

- 各功能与系统维护对应文档，统一入口为 `docs/systems/README.md`。
- 每次修改前，先查看系统索引和相关文档，确认是否已有功能、接口和规则；文档仅作为索引与参考，可能不完整或过时，必须再通过 IDEA 核对当前源码、依赖、类型和引用。文档未记载不代表功能不存在。
- 修改完成后同步相关系统文档；新增、删除、重命名和包迁移时同步索引、入口和链接。记录职责、公开接口、生命周期、配置、资源、协议、依赖以及已知限制的实际变化。
- 每次修改后在 `docs/systems/changes.md` 记录日期、范围、关键文件和实际检查结果；明确区分已实现、计划、历史证据、未验证及受阻内容。
- 解决或修正问题后，在对应系统文档记录问题现象、已确认的根因、修复方式和防止再次踩坑的维护要点；修改前检查这些记录，避免重复引入已解决的问题。推测与未验证结果必须明确标注，不能当作已确认根因。
- 文档补充不构成额外代码修改授权；生成输出保持只读，不在其中放入手写文档。

## 工具、编辑与并行

- 优先使用已有 Skill、MCP、IDE、工具和 API。
- 默认使用不抢占鼠标、键盘、窗口焦点或当前编辑状态的 MCP/API。需要并行开发时，优先使用独立工作树、项目目录或 IDE 实例隔离；不得并行修改同一物理文件。
- 启动或进入 Minecraft 客户端后，先最大化游戏主窗口。Photon 等编辑器必须嵌入游戏窗口打开，不创建独立 OS 编辑器窗口；既有独立宿主使用原生 dockIntoGameWindow 切回游戏内。按游戏主窗口确认实际最大化状态，不以内部布局状态代替。
- 连贯且步骤固定的操作合并为一次 MCP/API 调用或批处理，只在开始、结束及有分支或失败时读取必要状态，避免逐步重复查询。进入新测试世界优先复用开发环境的 Create Test World 快速入口；已在所需世界时直接继续，不重复进入。
- 项目文件只能通过 IDEA 编辑，包括 Java、资源、配置、Gradle 和 Markdown 文档。
- IDEA/MCP 不可用或无法完成编辑时，先说明并等待授权，不自动改用 `apply_patch` 或命令行编辑。
- 每次修改前后，都通过 IDEA/MCP 检查相关文件信息。
- 大型修改前后检查文件内容、错误、警告、语法、引用和 Git 状态；只改数值等极小修改时，只检查相关部分。
- 允许并行处理不同文件，但必须明确文件归属，禁止并行修改同一个文件。
- 目标文件已有用户修改时，先通过 IDEA/Git 对比，再在同一文件中最小范围合并，不覆盖用户修改。
- 完成代码修改后，必须通过 IDEA 执行代码格式化；常规修改仅格式化修改行或明确涉及的类，优先使用行范围。只有用户明确授权的整个项目整理任务才允许按包或项目范围格式化。
- 格式化默认关闭额外的导入优化和成员重排；需要这些操作时，只处理本次明确授权的范围。
- 格式化前确认文件类别与来源。用户提供的 JSON 等资源文件、数据生成输出、第三方文件和二进制资源不纳入自动格式化；需要修改资源内容时保持其原始排版，除非用户明确要求格式化该文件。
- 只修改当前任务明确涉及的内容，不进行无关重构、清理、重命名、格式化或修复。

## 修改规模与收尾

以下任一情况都属于大型修改：

- 涉及多个系统；
- 涉及多个文件；
- 重构；
- 包迁移；
- 数据结构变化；
- 网络协议变化。

大型修改完成后，必须通过 IDEA 的运行配置、MCP 和 IDEA 诊断完成：

- 项目编译；
- 数据生成任务（例如 `runData`）；
- 生成资源检查；
- 其他文件中过时调用的检查。

大型修改收尾发现与本次改动无关的既有问题时，只记录并说明需要扩大范围，等待确认，不直接处理。小改动不强制执行上述完整收尾流程。

`runData` 自动生成的文件和目录是只读输出，不允许直接修改，也不允许放入手写内容。生成结果不符合要求时，只修改生成源，再通过 IDEA 重新生成。生成完成后，使用 IDEA/Git 确认只产生预期文件和内容。

新增翻译键时，必须通过 IDEA/MCP 执行数据生成（`runData`），这是对默认不主动运行数据生成规则的明确例外。如果本次任务只新增翻译键，数据生成成功并确认生成结果后即可结束，无须额外执行编译、构建、测试或运行游戏。数据生成失败或受阻时，必须如实报告。

不得把未执行、被中断或被环境阻断的操作报告为成功。IDEA 检查通过的含义是：本次修改不新增相关错误或警告；无关的既有问题只记录，不要求清零。

## 复用已有能力

- 优先复用已知 `lib`、API 和接口。
- 频繁使用或多处共用的逻辑，必须集中提供 API 或工具入口；调用方通过该入口使用，不重复实现判定、状态修改或存储操作。入口应封装实际规则和生命周期，不为已有公共 API 增加无实际职责的重复代理。
- 新增系统、抽象、接口或依赖前，先通过 IDEA/MCP 检索项目源码、已有依赖、当前版本 API 和相关 Skill 文档。
- 如果可以组合已有接口实现需求，必须优先组合，不新增系统。
- 只有确认存在明确能力缺口后，才提出新增方案。
- 引入新的 `lib` 前，必须先说明能力缺口、必要性、影响、版本和维护成本，并得到确认。
- 复用 API 或 `lib` 时，以当前项目锁定版本的 IDEA 解析结果和本地文档为准，不直接套用其他版本示例。
- 过时调用检查以 IDEA 语义引用、Find Usages 和类型解析为主，必要时再使用文本搜索。
- 依赖 JAR、Minecraft 类及类路径源码通过 IDEA/MixinMCP 查询，不用命令行搜索、解压或自行反编译代替已有专用能力。
- 对单例、注册项及可能在注册阶段构造的对象，默认使用 `Supplier` 或等效延迟引用；不得在注册绑定完成前调用 `DeferredHolder#get()`。同时检查构造方法、字段初始化器和静态初始化器中的提前解引用；只有确认仅在游戏运行期创建的对象才直接获取。

## 版本与验证边界

- 当前项目版本以 IDEA 解析结果、项目配置和已锁定依赖为准。
- 小改动不主动执行编译、构建、测试、数据生成或运行验证。
- 大型修改按照本文件的收尾流程执行，并只报告实际完成的检查。
- 修改完成后保留用户已有的暂存、未暂存和未跟踪工作，不擅自重置、覆盖、暂存、提交或删除。

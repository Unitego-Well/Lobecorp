# Lobecorp Java、接口与包规范

本文件从项目根 AGENTS.md 按职责拆出，与根文件具有相同约束效力；仅在修改 Java、接口、系统边界或包结构时读取适用章节。用户当前明确指令仍优先。拆分不改变原规则，不授权顺带修改或主动运行。

## 常量、可见性与接口

- 只有多处使用、经常变更或属于规则数值的内容才提取为常量。
- 不机械提取所有字面值；仅在多处复用、属于独立可调规则、由配置或多个注册点共同管理，或内联含义不清时集中管理。控制器单次注册中的名称和过渡参数可直接写在注册处；已有实体属性作为权威来源时直接读取，不再定义重复数值。
- 技能前摇、持续、后摇和冷却等一次性生命周期配置直接放在注册 `Properties` 中，不在技能实现中重复保存。技能类仅提取复用或独立可调的规则参数；单次局部计算值可保留内联。
- 提取出的常量，以及本次大型修改涉及的既有常量，按下文注释必要性规则添加中文说明，保留代码本身无法直接表达的业务含义、单位或取值依据；不为常规注册声明机械添加注释。
- 可见性只能使用 `public`、`protected` 或 `private`，禁止包私有。
- 该可见性规则适用于当前任务涉及的既有成员。
- 默认采用最小必要可见性：仅本类使用为 `private`，子类使用为 `protected`，外部确有需求时才使用 `public`。
- 外部需要访问但不应直接暴露内部成员时，使用包装方法提供访问。
- 未明确要求时，不要私有化工具类的构造函数，也不要额外声明 `final` 类。
- Java、C# 中可通过 `import` 或 `using` 引入的成员，使用简洁调用形式，不用完整限定名调用。
- 编写或修改本次涉及的 Java lambda 时，优先使用安全等价的方法引用，省去冗余的单表达式代码块、`return` 和可推断参数类型；不得改变重载解析、泛型推断、构造时机、注册生命周期或异常语义，不扩大为无关清理。

## 系统边界与依赖

- 系统包括功能模块、包、事件、网络、动画、渲染和数据存储等子系统。
- 专门的系统只负责自己的职责，不在一个系统中混入其他系统的职责；只有明确的强依赖才允许跨系统协作。
- 能独立启用、禁用或替换的通常视为弱依赖；不能独立运行或替换的视为强依赖。
- 系统之间保持单向依赖。
- 强依赖只能通过被依赖系统的公开接口交互，不能直接访问内部实现。
- 发现现有系统违反边界时，仅在当前任务范围内且确有必要时调整；否则记录问题并等待确认。
- 网络包必须严格遵循当前 `network` 包的分类，并使用对应的 `ITo...Payload` 接口；不得另建平行的 Payload 分类或接口体系。

## 接口命名

- 顶层常规接口名称必须以 `I` 开头；纯粹用于注册项、工具方法或常量归集的接口除外，按实际职责判断，不仅凭包名或当前名称分类。
- 桥接接口、Mixin Accessor 及内部回调接口保留原名称；存量整理只重命名已确认的 12 个顶层常规接口，不扩展到这些例外。名称对应见 [系统修改记录](../systems/changes.md)。
- 接口重命名必须通过 IDEA 语义重构同步实现、引用、Mixin 配置及相关文档，不改变接口行为或数据标识。

## Java 25 语法与注释

- 本项目采用 Java 25。处理 Java 开发任务前必须读取 [Java 25 语法与注释规范](../java-25-language-and-comments.md)，以 Java 25 已正式发布的功能为基准，默认不启用预览或孵化功能。
- 新编写及本次明确修改范围内的代码，必须按专项规范使用适用且语义等价的现代写法，包括模式匹配、switch 表达式、record 模式、未命名变量／模式、局部类型推断和灵活构造器；保持框架签名、注册生命周期与原有行为。
- 新增或本次修改的 Javadoc 文档注释必须使用 `///` Markdown 形式；普通实现说明保持 `//`，必要多行说明使用 `/* ... */`。注释说明仍为中文，技术片段与第三方声明遵守下节规则。
- 本规范不授权批量改写历史代码或注释，不机械采用模块导入、紧凑源文件、record 或 sealed 改变项目结构。

## 注释语言

- 常规注册声明，以及从代码结构、类型、调用和参数即可直接看明白的内容，不需要注释；删除仅重复这些事实、没有补充信息的注释，不套用“登记项”“保持既有约定”等空泛模板。
- 变量名清楚本身不算“非常明了”，不得仅凭变量名删除注释。业务含义、单位、取值依据、边界、所有权、生命周期、特殊注册时机和具体兼容约束仍须保留必要说明。
- 注释的说明文字必须使用中文，包括行注释、块注释、Javadoc 和常量说明；新增及修改注释均遵守此规则。
- 技术标识符、类型/API 名称、Javadoc 标签、URL、协议/代码示例和 IDE 控制指令保留原文，不将这些必要技术片段误当作外语说明翻译。
- 第三方代码的版权与许可证原始声明保留原文，不改写署名、授权信息或条款。

## 方法与代码块

- `if`、`else`、`for`（含增强 `for`）、`while` 和 `do` 的语句体必须使用大括号，即使只有一条语句也不得省略；`else if` 可保持连续分支形式，每个条件分支的语句体仍须带大括号。
- 使用空行分隔条件检查、循环、异常处理及相邻的独立逻辑块；条件检查与后续正常处理之间留空行，不拆开 `else`、`catch` 或 `finally` 与其对应代码块。
- `if` 优先采用前置条件检查和提前返回，减少正常路径的嵌套；循环内可使用提前 `continue`。保持原有副作用、执行顺序、异常和资源释放语义，不机械改写需要分支汇合的逻辑。
- 方法、构造函数及复杂 lambda 尽量不超过格式化后的 100 行；超过时优先按独立职责拆分，避免通过压缩语句、删空行或任意截断来满足行数。
- 复杂逻辑拆成职责明确的独立方法，入口只保留清晰的流程；优先复用已有方法，不为简单逻辑新增无实际职责的抽象。

## 包与职责分类

- 所有注册相关内容统一放入 `registry` 包；客户端注册也遵守此规则。
- 所有客户端内容统一放入 `client` 包，但注册放入 `registry`，配置放入配置包，事件监听放入 `events` 包，Mod 自定义事件放入 `event` 包。
- 所有事件监听统一放入 `events` 包；`event` 包负责 Mod 自己的事件类，`events` 包负责监听、订阅和分发。每个事件只允许存在一个监听入口。
- 类按功能域和职责放入对应包或子包，不把编辑器、运行时、渲染、配置和资源处理等不同职责全部堆入一个包，也不机械为每个类创建单独的包。
- 包整理前必须提交具体计划，列明来源包、目标包、涉及类、迁移理由及 Java 引用、Mixin 配置和资源引用的影响；得到用户同意后，才通过 IDEA 语义重构执行移动。
- 用户要求并行任务时，按互不重叠的文件范围分配任务；包移动与引用更新由一个负责人执行，避免跨包引用文件被并行覆盖。
- 所有工具类统一放入根 `util` 包，可在其下按作用继续分包，并以 `Util` 结尾命名；不在其他功能域建立平行的工具包。
- 包分类按“作用 → 类型”组织，保留 `client`、`registry`、`mixin`、`config`、`event`、`events`、`network` 和 `util` 等统一职责入口，在入口下按功能域细分。
- 实体及其 AI、技能、状态和属性放入 `world.entity`；物品、效果和命中框分别归入简化的 `world.item`、`world.effect` 和 `world.hitbox`，具体结构参考原版并按项目需要简化，不使用 `level` 作为该入口。
